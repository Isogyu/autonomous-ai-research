結論

中身を読み切れていないコードを動かすなら、通信と書き込み先を絞れる方式が要る。Podman のコンテナは絞る指定を持つが、Windows では仮想化の機能の許可が前提で、指定が実際に効くかは環境ごとに確かめる必要がある。

対象の読者

社内の Windows PC で、AI が書いたコードを動かして試そうとしている開発の担当 — AI が書いたコードは、中身を全部読む前に動かすことがある。どこで動かすかで、PC と社内のデータへの影響の範囲が変わる

適用の条件

  • AI が書いたコードを、全部を読む前に社内の PC で動かしたい
  • 社内のデータや認証情報に届く PC で作業している

重要な制約

  • 社内の Windows PC では、どの方式も動かしていない
  • WSL 2 と仮想化の機能を使えるかは、社内で未確認
  • コンテナに替えるだけでは、隔離は成立しない

要点

  • そのまま動かすと、自分の権限で届く範囲すべてに触れる
  • Podman のコンテナは、通信と書き込み先を指定して絞れる
  • どの隔離の方式も、社内の許可の確認が先に要る

動かす場所で、隔離と、要る確認はどう違うか

  • そのまま実行: 隔離の範囲 は なし、社内で要る確認 は なし
  • WSL 2 の隔離機能: 隔離の範囲 は 未確認、社内で要る確認 は WSL 2 の許可
  • Podman コンテナ: 隔離の範囲 は 指定した範囲、社内で要る確認 は 仮想化の許可

そのまま実行する場合は、隔離がなく、追加の確認も要らない。Claude Code の WSL 2 でのサンドボックスは、制限する範囲を確かめておらず、WSL 2 の利用の許可が要る。Podman のコンテナは、通信と書き込み先を指定した範囲に絞れるが、Windows では仮想環境（WSL 2 か Hyper-V）の利用の許可が要る。

比較の条件と根拠

  • 比べたのは、公式の文書に書かれた機能の有無。同じ課題を各方式で動かした実測ではない
  • 「そのまま実行」は、追加の仕組みを使わない場合。動かしたコードは、利用者の権限で届く範囲すべてに触れられる
  • Podman の公式の文書は、通信を持たせない指定と、ルートを読み取り専用にする指定を説明している
  • 同じ文書は、資源の上限の指定が使えない構成があると書いている。指定を受け付けることと、効くことは別
  • Podman Desktop の公式の文書によると、Windows では WSL 2 か Hyper-V の仮想環境が要る
  • Claude Code の公式の文書は、サンドボックスが WSL 2 でだけ対応すると書いている。何を制限するかは、このページからは分からない

検証の状況

情報紹介・未再現: 各提供元の公式の文書を読み比べただけ。社内の Windows PC では、どの方式も動かしていない

確かめていない点

  • 社内で WSL 2、Hyper-V、Podman を使えるか
  • Claude Code の WSL 2 でのサンドボックスが制限する範囲（該当の文書を読んでいない）
  • Windows 上の Podman の仮想環境で、指定した制限が実際に効くか（Linux での確認は別の投稿候補 podman-isolation-verify にある）

根拠の強さ

中程度: 各提供元の公式の文書（一次情報）に基づく。ただし、方式どうしを同じ条件で比べた実測ではなく、社内の環境での確認もない
