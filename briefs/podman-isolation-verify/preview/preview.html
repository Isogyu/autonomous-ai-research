結論

コンテナの制限は、指定したあとに、コンテナの中から確かめられる。Linux の Podman では、確かめる手順が通った。Windows ではまだ確かめていない。

対象の読者

社内の Windows PC で、AI が書いたコードをコンテナで動かそうとしている開発の担当 — コンテナに制限を指定しても、環境によっては効かない。効いているかを、動かす前に確かめる方法が要る

適用の条件

  • AI が書いたコードを、Podman のコンテナで動かそうとしている
  • Podman を使える環境がある（社内の Windows PC については、利用の可否が未確認）

重要な制約

  • 確認は Linux だけ。Windows は未確認
  • 手順のコードは未マージ（PR #12）

要点

  • 制限は、指定しただけでは効いたか分からない
  • コンテナの中から、通信・書き込み・上限を確かめる
  • 確かめていない構成では、実行しない作りにした

隔離を、どう確かめるか

    1. イメージを取得して固定する
    1. 制限を指定して起動する
    1. 中から制限を確かめる（通信・書き込み・上限・権限）
    1. 通らなければ実行しない

手順は 4 つ。まず、動かすイメージを取得して内容を固定する。次に、通信なし・読み取り専用・資源の上限を指定してコンテナを起動する。そのコンテナの中から、通信に出られないこと、書き込めないこと、上限の値、権限を確かめる。1 つでも通らなければ、その環境ではコードを実行しない。

必要な環境

Podman と、取得済みの Python のイメージ。このリポジトリの PR #12（未マージ）のコード。確かめたのは Linux だけ

手順

  1. PR #12 のブランチ（feat/windows-podman）を取得する
  2. Python のイメージを取得し、ダイジェストつきの名前を控える
  3. 隔離の検証のコマンド（aar podman verify）を実行する
  4. 項目ごとの結果を読む。通らない項目があれば、指定を緩めずに、構成を見直す

結果

  • Linux の CI（Podman 5.7.0、rootless、cgroups v2）で、確認のテスト 5 件が通った
  • PostgreSQL の起動・接続・停止も、同じ環境の Podman で通った

失敗した例・つまずいた点

  • テストが、イメージに元からある環境変数を、秘密情報の漏れと誤って判定した。判定の条件を直した
  • Windows と、別の場所で動く Podman への接続は、試せる環境がなく、結果がない

検証の状況

自環境で検証済み: このリポジトリの CI（Linux）で、コンテナの中から制限を確かめるテストを動かして通った。Windows では動かしていない

自分たちの実測

  • 環境: GitHub Actions の Linux の実行環境。Podman 5.7.0、rootless、cgroups v2、crun
  • 実施日: 2026-11-25
  • 結果: 隔離の確認のテスト 5 件がすべて通った。通信に出られない、ルートに書けない、上限の値が指定どおり、権限がない、root 以外で動く、時間切れのあとに何も残らない
  • 記録: PR #12 の CI の実行 45628443267（podman の経路）。テストは tests/test_podman_real.py
  • 手順:
  • 動かすイメージを取得し、ダイジェストで固定する
  • 通信なし・読み取り専用・資源の上限・権限の削除を指定して、コンテナを起動する
  • コンテナの中から、通信、書き込み、上限の値、権限、利用者を調べる
  • 時間切れのあとに、コンテナとプロセスが残っていないことを調べる
  • この実測が確かめていない範囲:
  • Windows 上の Podman の仮想環境（WSL 2、Hyper-V）
  • クライアントとは別の場所で動く Podman への接続
  • rootful の構成

確かめていない点

  • Windows 上の Podman の仮想環境で、同じ確認が通るか
  • クライアントとは別の場所で動く Podman で、作業用のフォルダーを渡せるか
  • 社内で Podman を使えるか

根拠の強さ

中程度: 自分たちの実測で、手順と記録が残っている。ただし環境は Linux の CI の 1 種類だけで、社内の Windows PC での結果ではない
