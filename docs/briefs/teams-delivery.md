## 2. 方式の比較

「画像つきの投稿」と「Adaptive Card」は、別の方式として扱う。

| | A. 人が投稿する（本文＋画像を貼る） | B. Workflows の webhook で Adaptive Card を送る |
|---|---|---|
| 送信の実装 | 要らない | 要る（未実装） |
| 社内で要る確認 | 投稿先のチャネルと、投稿してよい内容 | A に加えて、Workflows の利用の可否、ワークフローの持ち主、webhook の URL の管理 |
| 図解カード | PNG にして貼る（SVG のままでは、Teams の画像として使えない見込み。PNG への変換は未実装） | 画像を使うなら、Teams から取得できる https の場所に置く必要がある。社内だけに見せたい画像を、公開の場所に置くことはできない。**置き場所が決まるまでは、画像なしで、同じ内容を文字で出す** |
| 画像を見られない人 | 本文に、図の内容を文章で入れる（実装済み）。貼った画像の代替テキストは、投稿する人が Teams で設定する | カードの文字のブロックに、同じ内容を入れる（下書きの JSON は実装済み） |
| 投稿者の表示 | 投稿した人 | Workflows のボット |
| 重複・再試行・訂正 | 人が行い、記録する | 仕組みが要る（下の 3） |
| 向いている段階 | **最初の小規模の試行** | 人が確かめる運用が安定し、社内の確認が済んだあと |

**案: 最初は A。** 少数の読者に見せる段階では、送信の仕組みは要らない。プレビューの本文を貼り、カードを画像にして添える。
B に進むかどうかは、試行の結果と、社内の確認のあとで決める。どちらも、社内の環境では試していない。

### カードを画像にする方法（未実装・未確認）

プレビューのカードは SVG。Teams に貼るには PNG が要る。候補は次のとおりで、どれも社内の PC では試していない。

- ブラウザーでプレビューを開き、カードの部分を画面の切り取りで画像にする（道具の追加が要らない。最初の試行はこれで足りる）。
- ブラウザーのヘッドレスの機能で SVG を PNG にする（開発中の表示の確認は、macOS の Chrome でこの方法を使った）。
- 変換のライブラリを足す（フォントが環境に依る。日本語のフォントが無いと、文字が出ない）。

## 3. 送信を実装するときの設計（いまは作らない）

- **承認との結び付き**: 送るのは、承認済みで、内容のハッシュが承認のときと同じ候補だけ。送る直前に、もう一度確かめる。
- **重複の防止**: 冪等キーは「候補の id ＋ 内容のハッシュ ＋ 投稿先」。送信の前に記録を調べ、同じキーの成功があれば送らない
  （いまの `record-post` と同じ規則）。訂正版は、内容が違うので別の投稿になる。
- **再試行**: 通信の失敗や、絞り込み（1 秒 4 件）のときだけ、間隔を延ばして数回まで。4xx の応答（形式の誤り、権限）は再試行しない。
  webhook は、受け付けたことしか返さないので、「送れた」と「表示された」は別に記録する（表示は、人が確かめる）。
- **送信の結果**: 記録に、時刻、投稿先の名前（URL は書かない）、応答の状態、試行の回数を残す。
- **訂正**: 元の投稿は消さず、訂正版を新しい投稿として出し、元の投稿に返信で訂正版を示す。webhook から過去の投稿を書き換えられるかは未確認。
- **認証情報**: webhook の URL は、それ自体が秘密（知っていれば投稿できる）。リポジトリ、投稿候補、記録、ログ、例外の文面に入れない。
  置き場所は `.env`（Git に入れない）か、社内で決められた秘密の保管の仕組み。ログに出すのは、投稿先の名前だけ。
  秘密情報の検査（`workspace.SECRET_PATTERNS`）に、webhook の URL の形を足す。
- **定期の実行**: 作らない。人が、1 件ずつ送る操作にする。自動の配信へ進む条件は [trial-plan.md](trial-plan.md)。
- **社内のデータを外部へ送らない**: この機能は、モデルを呼ばない。将来、文章の下書きにモデルを使うなら、社内のデータを外部のモデルへ
  送ってよい範囲を先に確かめる（未確認）。
