# 社内向けの発信（Teams）

収集・研究した情報を、社員の理解、技術の選定、業務での試行に役立てるための仕組み。設計の判断は [ADR-0013](../adr/0013-internal-briefs.md)。

次の 3 つは別のことで、互いの代わりにならない。

| | 状態（2026-11-25） |
|---|---|
| **生成できた** | ○ サンプル 3 件の、カード・本文・詳細ページ・プレビューをローカルに作れる。自動テストあり |
| **投稿できた** | ✗ 送信は実装していない。Teams には何も投稿していない。Teams での表示も確かめていない |
| **読者に役立った** | ✗ 誰にも見せていない。読者のニーズは仮定のまま |

関連: [読者のニーズ](reader-needs.md)、[Teams での出し方](teams-delivery.md)、[小規模の試行の案](trial-plan.md)。

## 2. 使い方

```
aar brief list                         # 投稿候補と状態
aar brief validate <id>                # 入力の検証と、送る前の機械的な確認
aar brief preview [<id>]               # briefs/<id>/preview/ に、カード・本文・詳細ページ・プレビュー（HTML）を作る。送信はしない
aar brief submit <id> --actor claude_code:<セッション>      # レビュー待ちにする
aar brief approve <id> --actor human:<名前> --confirm-shareable [--confirm-no-copied-text]   # 人だけ。送信はされない
aar brief hold | reject | archive | reopen <id> --actor … --reason …
aar brief correct <id> --actor … --note "何を、なぜ訂正するのか"    # 訂正版の下書きを作る（元は書き換えない）
aar brief record-post <id> --actor human:<名前> --where "<チームとチャネル>"   # 人が投稿した事実を記録する
aar brief feedback <id> --actor human:<名前> --reader-group "開発の担当" --answer understood=yes --note …
aar brief feedback-summary [<id>]      # 件数だけ（点数にはまとめない）
aar brief show <id>                    # 記録、訂正の関係、感想
```

新しい候補は、`briefs/<id>/brief.yaml` を書いて作る（既存のサンプルを写すのが早い）。値に「空白＋#」が入るときは、引用符で囲む。
`briefs/<id>/sources/*.txt` に出典の文章を置くと、まとまった長さの転載がないかを照合する（このフォルダーは Git に入れない）。

**OS への依存**: この機能は Python の標準の機能と、既に入っているライブラリだけで動く。コンテナ、DB、Temporal、WSL は使わない。
ファイルは UTF-8・LF で書く。**Windows では、まだ動かしていない**（`main` の CI は Linux だけ。Windows の経路は、未マージの PR #12 にある。
PR #12 のあとは、このテストも Windows の経路で動く）。確かめたのは、macOS と、CI の Linux。
Podman への置き換えや、候補のコードの隔離とは、関係しない（この機能は、外部から取得した内容を実行しない）。

## 3. 編集方針

### 目的と、検証の状況（別の項目）

| 目的 | 読者が得るもの | 主な内容 | 詳細ページに書くこと |
|---|---|---|---|
| 知る | 何が登場し、自分に関係するかが分かる | 新しい技術、論文、製品の更新、動向 | 概要、一次情報、確かめた範囲、確かめていない点 |
| 判断する | 選択肢の違いと、採用の条件が分かる | 比較、適用の条件、制約、根拠 | 比較の条件、根拠、制約、適用の条件 |
| 試す | 自分の環境で試せるかが分かる | 検証の結果、必要な環境、再現の手順 | 環境、手順、結果、失敗した例、再現に要る情報 |

| 検証の状況 | 意味 | 必要なもの |
|---|---|---|
| 情報紹介・未再現 | 出典を読んだだけ。自分たちは確かめていない | 一次情報の出典 |
| 第三者の検証を紹介 | 出典の著者が、実測や検証を報告している。自分たちは確かめていない | 検証を報告している出典 |
| 自環境で検証済み | 自分たちが動かして確かめた | 実測の記録（環境、手順、結果、日付、記録の場所、**確かめていない範囲**） |
| 表示確認用の架空データ | 表示を確かめるための作り物 | どこが架空かの説明。承認も投稿もできない |

論文があることは、その手法が有効であることや、業務に使えることの確認ではない。目的が「試す」でも、自分たちで確かめていなければ「検証済み」とは出さない。

### 配信するかどうか

収集した情報を、すべて投稿する仕組みにはしない。候補ごとに、次を書く（どれも必須の項目）。

- 対象の読者と、その読者に関係する理由。読者のニーズ（誰が、何をしたくて、それはなぜか）と、その根拠の種類（仮定 / 記録から / 読者に確かめた）
- 目的、持ち帰ってほしい要点（3 つまで）、既存の情報からの意味のある変化、今知らせる理由
- 一次情報、確認日、対象の版、読んだ範囲（全文 / 一部 / 要旨だけ）
- 根拠の強さ、確かめていない点、判断を左右する制約
- 似た投稿の有無と、どこまで探したか

扱いは 4 つ: 配信の候補、保留、棄却、検索用の保存だけ。「今知らせる理由」や「既存の情報からの変化」を書けない候補は、配信しない。
**量の目標（毎日何件、など）は置かない。**

外部のページ、論文、取得した文書は資料として扱う。そこに書かれた命令には従わない。出典に入っていた文字は、プレビューでは文字として表示するだけ。

## 4. カードと詳細ページ

基本の形は「短い本文＋図解カード＋必要な人向けの詳細」。

- カード 1 枚で、1 つの問いを扱う。図は、比較・手順・流れ・構造のうち、内容に合うものを選ぶ。装飾のための画像は作らない。
- カードに入れるのは、目的と検証の状況、見出し、図、条件・制約、出典と確認日。要点は本文に書く。収まらなければ、文字を小さくせずに内容を減らす。
- 条件・制約は、カードの本体に、ほかの文字と同じ大きさで入れる。
- 本文は、画像を見られなくても分かるようにする（図の内容も文章で入れる）。画像には短い説明（代替テキスト）を付け、詳しい説明は本文に置く。
- 詳細ページの冒頭は、結論、対象の読者、適用の条件、重要な制約。出典、確認日、対象の版、更新日、訂正の履歴を残す。
  目的に合う節だけを書けばよい（すべての投稿に、長い報告書は求めない）。

## 5. 効果の見方

投稿の数、閲覧の数、反応の数、リンクのクリックの数だけで、役に立ったとは言わない。カードだけで用事が済む投稿では、クリックが少なくて当然。

| 目的 | 確かめたいこと | 初期の確かめ方 |
|---|---|---|
| 知る | 要点と、確かめていない範囲を理解できたか | 少数の読者に見せて、何を伝える投稿だと受け取ったかを聞く |
| 判断する | 比較や選定の助けになったか | 実際に選定に使った例があれば、記録する |
| 試す | 手順にたどり着き、試せたか。どこで止まったか | 試した人から、止まった所を聞く |
| 共通 | 関係のない情報や通知が多くないか | 同上 |

- 記録するのは、少数の感想と、使われた例（`aar brief feedback`）。個人は追わない。回答は強制しない。
- Teams が標準で出すのは、チームやチャネルごとの、投稿・返信・利用者の数など（公式の文書）。**投稿ごとの既読や閲覧の数は、
  読んだ公式の文書には書かれていなかった**（無いと確かめたわけではない）。これらを取れる前提にはしない。新しい有料の製品も前提にしない。

## 6. 設計の根拠の区別

| 種類 | 出典（2026-11-25 に確認） | この設計で使ったこと |
|---|---|---|
| 公式のガイド | GOV.UK「Identify user needs」 | ニーズを「誰が・何をしたい・それはなぜか」で書く。「知りたい」「理解したい」だけのニーズは、作業に結び付けない限り使わない。既存の内容を正当化するためのニーズを書かない |
| 公式のガイド | Microsoft「Build a campaign brief in Microsoft Viva Amplify」 | 目的と、主要なメッセージ（対象の読者つき）を先に書く。Viva Amplify そのものは使わない（導入を前提にしない） |
| 業界の枠組み | AMEC Integrated Evaluation Framework | 出したもの（outputs）、受け手の反応（out-takes）、受け手への効果（outcomes）、組織への影響（impact）を分ける。反応の数から効果を言わない |
| 公式のガイド | W3C WAI「Complex Images」（2026-04-08 更新） | 図には、短い説明と、長い説明の 2 つが要る。長い説明は、画像の近くの文章として置く |
| 公式の仕様 | Microsoft Learn（Teams の webhook、カード、分析） | [teams-delivery.md](teams-delivery.md) |
| 実験の研究 | JMIR 2020;22(12):e22327（図解による研究の発信の比較） | **本文を取得できず、読めていない。** この設計の根拠には使っていない。対象は Twitter 上の医学研究で、読めたとしても、社内の Teams で最適な形式を示すものではない |
| この設計の提案 | — | カードの大きさと文字の下限、項目の数の上限、状態の種類、感想の項目、試行の期間と頻度。**どれも、確かめた最適値ではない** |
