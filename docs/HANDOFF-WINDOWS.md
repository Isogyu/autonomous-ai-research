# 引き継ぎ: 社内の Windows PC で作業を始めるエージェントへ（2026-11-26）

この文書は、このリポジトリを社内の Windows PC にクローンして、実装を引き継ぐエージェント（Claude Code）に向けて書いた。
書いたのは、個人の Mac で作業していたセッション。**あなたは、この文書と、リポジトリの中身だけを手がかりに始めることになる。**
Mac での会話、Mac にあるデータ、Mac の認証は、そちらにはない。

守ることは [CLAUDE.md](../CLAUDE.md) にある（先に読む）。とくに、**ソフトウェアを勝手に入れない。**

## 1. これは何か

論文を集め、検証の企画を作り、選ばれた企画について実験・独立監査・公開準備までを自動で進める基盤（[README.md](../README.md)）。
あわせて、基盤そのものの改善候補を比べる仕組み（[improvement.md](improvement.md)）と、社内の Teams 向けの発信の下書きを作る仕組み
（[briefs/README.md](briefs/README.md)）がある。

個人の Mac（macOS、Docker）で作り、動かしてきた。2026-11-25 に、開発と運用の対象を**社内の Windows PC と Podman** へ移すことになった。
コードはその向きに直してあるが、**Windows の実機では、まだ一度も動かしていない。** そこから先が、あなたの仕事。

### このクローンに無いもの

このため、いまの Windows の環境には、研究が 1 件もない。`aar projects list` が空でも、`aar improve list` が空でも、正しい。

## 3. 最初の確認（読むだけ。何も入れない、何も変えない）

1. `git log --oneline -5` と `git status`。`src\aar\proc.py`、`src\aar\container.py`、`src\aar\ctl.py`、`docs\windows\` があるか。
   **無ければ、#12 の内容が `main` に入っていない。** そこで止まって、利用者に伝える（自分でマージしない）。
2. `git ls-files --eol | Select-String 'w/crlf'`。何も出なければよい（改行が変換されていない）。出たら、止まって伝える。
3. 既に入っているものを調べる: `Get-Command python, py, git, gh, podman, temporal, node, claude, codex, wsl -ErrorAction SilentlyContinue`。
   **無いものを入れない。** 一覧にして、利用者に見せる。
4. 利用者に確かめてから、`powershell -NoProfile -File .\scripts\windows\Probe-Environment.ps1`（読み取りだけ）。
   結果には利用者名とホスト名が入るので、リポジトリに入れない。外部にも送らない。
5. [windows/setup.md](windows/setup.md) の 0 の表（社内の許可）を、利用者に聞いて埋める。分からない項目は「未確認」のままにする。

ここまでで、導入は 1 つもしていないはず。

## 4. 次にやること（この順で。どの段も、利用者の承認を得てから）

1. **実行方式を決める**（A: WSL2 / B: Windows ネイティブ）。決めるのは利用者。あなたは、probe の結果と社内の回答を整理して、選択肢を示す。
   どちらも許可されなければ、「ローカルでの安全な実行は未成立」と報告して止まる。決まったら、ADR-0012 の状態を更新する。
2. **必要なものの導入**。README の「必要なもの」と、3 で調べた結果の差分を示し、1 件ずつ承認を得る。入れるのは、利用者か、承認を受けたあなた。
3. **DB を使わないテスト**を、この PC で動かす（`.\.venv\Scripts\python.exe -m pytest -q -rs`）。CI の Windows では 109 件が通っている
   （その後、発信のテストが増えている）。この PC で落ちるものがあれば、それが最初の実機の発見になる。直す前に、原因を記録する。
4. **Podman の確認**（[windows/setup.md](windows/setup.md) の 3）。`aar podman info` で、rootless かどうか・リモートかどうか・cgroups を記録する。
   `aar podman verify` を動かし、通らない項目をそのまま記録する。**とくに分からないのは**、Windows のクライアントから仮想環境へ、
   作業用のフォルダーをマウントできるか（通らなければ、実験は実行されない。制御された転送は未実装）と、rootless で資源の上限が効くか。
5. **起動**（`.\scripts\aarctl.ps1 start`）。検証用の DB と、新しい名前空間（`AAR_TEMPORAL_NAMESPACE=aar-win`）で。`start` は、実機で一度も動かしていない。
6. **DB と Temporal を使うテスト**。Temporal の実行ファイルを外部から取得する動作があるので、先に確かめる（CLAUDE.md の表）。
7. **実行担当の CLI**。`aar doctor` が、実際に起動する実行ファイルを表示する。`.cmd` のランチャーしか無い場合の扱いは `src\aar\proc.py`。
   認証は、利用者がこの PC で行う。Codex の OS サンドボックスの Windows での挙動は、調べていない。
8. **台本での一巡**（`AAR_MODE=mock`）。外部の API と CLI を呼ばずに、検証用の研究を 1 件通す。
9. 結果を [STATUS.md](STATUS.md) に、「実装済み」「CI で確認済み」「この PC の実機で確認済み」を分けて書き、PR にする。

実機で分かったことは、文書を直す材料になる。`docs/windows/` の手順は、実機を通さずに書いたもので、間違いがあるはず。
見つけたら、手順のほうを直す（動かない手順を、動いたことにしない）。

## 6. 知っておくこと

- **作りの決まり**: 研究の担当（Claude Code）にはシェルを渡さない。実験のコードは、オーケストレーターが隔離して動かす。
  監査の担当（Codex）は、対象の複製だけを読む。品質ゲートは、方針ファイルのハッシュを研究に固定して守る。
- **隔離**: 実験と、改善候補の評価は、`aar podman verify` に通った構成でだけ動く。通っていなければ、拒否される（それが正しい動作）。
  「Podman に替えたので隔離できた」とは言えない。効いているかは、コンテナの中から確かめた結果で言う。
- **文字コードと改行**: 基盤が書くファイルは UTF-8・LF。Python は UTF-8 モード（`PYTHONUTF8=1`）で動かす。`.gitattributes` で、Git の改行の変換を止めてある。
  事前登録や評価器はバイト列のハッシュで固定しているので、CRLF になると別物になる。
- **PowerShell のスクリプト**は、BOM つきの UTF-8 で保存してある（Windows PowerShell 5.1 が、BOM のない UTF-8 を別の文字コードで読むため）。
  編集するときに、BOM を落とさない。
- **YAML**: 値の中の「空白＋#」から後ろはコメントになり、文が欠ける。引用符で囲む（発信の候補では、読み込みで検出して止める）。
- **時刻**: DB は UTC。表示と、日次・週次の区切りは `AAR_TIMEZONE`。CLI が表示する利用上限の解除時刻は、OS の設定で読む。
- **利用上限**: 上限に達したら、解除の見込みまで問い合わせない。回避のための再試行をしない。長い実行の前に `aar limits` を見る。
- **費用**: Claude Code と Codex は定額契約のログインで動かす前提。従量課金の API キーは使わない、子プロセスにも渡さない。
  社内でどの契約を使うかは未確認。
- **Mac での経緯の詳細**は [HANDOFF.md](HANDOFF.md)（Mac の視点で書かれている。研究の ID や `pmset` の話は、Mac の環境のこと）。

## 7. 困ったとき

- 道具が無い、権限が無い、通信が通らない → 止まって、何が起きたかをそのまま伝える。回避しない。入れない。
- 手順が実機と合わない → 手順が間違っている可能性が高い。合わなかった点を記録して、利用者に伝える。
- 何を確かめたのか自信がない → 確かめていないと書く。
