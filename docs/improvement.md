# 基盤の改善候補（台帳と比較評価）

外部の研究と自分の実行の記録から改善の候補を見つけ、隔離した環境で現行方式と比べるための仕組み。設計判断は [ADR-0011](adr/0011-improvement-loop.md)。
ここには、既存の実装との対応、使い方、最初の実証の結果を書く。**稼働中の基盤には自動で反映しない。**

次の 3 つは別の結論で、互いの代わりにならない。
- コードの実装が済んだこと（この文書とテストで確かめられる範囲）
- 研究能力が上がったこと（**今回は主張しない**。測ったのは基盤の一部の性質だけ）
- 長期の無人運転を承認できること（別件。`docs/STATUS.md` の未確認の経路が残っている）

> 2026-11-26 追記: 評価の隔離は、検証済みの Podman のコンテナに変わった（[ADR-0012](adr/0012-windows-podman.md)）。
> 候補のファイル・`child.py`・課題の入力を標準入力で渡し、マウントもネットワークも持たせない。イメージは `AAR_IMPROVE_IMAGE` に
> ダイジェストつきで指定し、先に `aar podman verify` を通す。これは評価器の変更なので、評価器のハッシュが変わり、下の一巡で固定した
> 評価計画での新しい実行は比較されない（決まりどおり）。**最初の候補の棄却と、採否の基準は変えていない。**
> 候補を作る側の隔離は未完成のままで、既定では生成を拒否する（`AAR_IMPROVE_ALLOW_UNISOLATED_GENERATOR`）。

## 2. 仕組み

```
実行の記録（読むだけ）──▶ 弱点の抽出 ──▶ 候補（台帳）
                                          │
評価計画と課題を固定 ──▶ 現行方式の基準値 │（候補を作る前）
                                          ▼
              基盤の複製（リモートなし）で候補を作る ──▶ 差分の検査（許可リスト、保護領域）
                                          ▼
   候補のファイルだけを隔離した別プロセスで実行 ──▶ 決定的な採点 ──▶ 機械的な採否 ──▶ 採用候補 / 棄却 / 保留
```

- 対象（いまは 1 つ）: `fix_context` — 修正担当へ渡す、監査の指摘の文脈の組み立て（`src/aar/engine/fix_context.py`）。
- 主指標: 指摘が参照している主張・証拠の ID のうち、その定義（主張の本文、証拠の所在）が文脈に入っている割合。
- 守ること（1 件でも違反すると棄却。主指標では相殺しない）: 出力が JSON として読める、指摘を落とさない、現行方式が渡していた項目の値を欠かさない、
  長さが予算以内、同じ入力に同じ出力。ほかに、参照されていない項目を入れすぎない、どの課題でも現行方式を下回らない、文脈が長くなりすぎない。
- 標本の下限: 封印評価に、開発に使っていない実物の課題が 3 件・2 グループ以上。満たさなければ、指標が良くても保留（改善は未確認）。

### 使い方

```bash
export AAR_ACTOR=claude_code:session        # 操作主体。human / claude_code / codex / scheduler のどれかで始める。省略はできない
aar migrate                                  # 表を作る（稼働中の DB への適用は、人が判断する）
aar improve areas --sync                     # 領域と外部の資料を台帳に入れる
aar improve scan --propose                   # 実行の記録から弱点を拾い、候補として登録する
aar improve plan                             # 評価計画と課題を固定し、現行方式の基準値を測る（候補を作る前に）
aar improve generate <候補ID> <計画ID>        # 実行担当に、基盤の複製の中で候補を作らせる（モデルの呼び出し 1 回）
aar improve eval <候補ID> <計画ID> --split select
aar improve eval <候補ID> <計画ID> --split sealed     # 封印評価。候補を選び終えてから 1 回だけ
aar improve decide <候補ID> <計画ID>          # 採否を機械的に判定して記録する
aar improve show <候補ID> --patch ; aar improve list 証拠の保全 --status rejected
```

封印評価の課題と seed、実行の生の出力、候補の複製は `var/improve/`（Git の対象外）に置く。

## 3. 調べる対象として登録した 10 領域

`aar improve areas` で表示できる（`src/aar/improve/areas.py`）。どの領域も、既存のどの問題に効くという仮説か、比べる相手、必要な資源、
採用しない条件を持つ。**登録しただけで、実装も常時実行もしていない。** 外部の資料 12 件は、2026-11-25 に到達できることと版を確かめた。
arXiv の 7 件は要旨のページだけを読んだ（本文は読んでいない）。別の環境やベンチマークでの改善を、この基盤での改善の証拠にはしない。

## 4. 最初の実証（2026-11-25）: 修正担当へ渡す文脈

台帳の写しは [improvement/2026-11-25-first-cycle.json](improvement/2026-11-25-first-cycle.json)（候補の差分、計画、実行、判定、操作の記録）。
台帳は、稼働中の DB ではなく専用の DB（`aar_improve`）に作った。

### 問題と根拠（実物の記録）

研究監査の修正 5 回（2 つの研究）で、修正担当に渡した指摘が主張の ID を 26 件参照していたが、その主張の本文は 1 件も渡していなかった。
研究2の限界文書にある「修正担当に主張の本文が渡っておらず、内容を特定できないまま対応していた」という記録と一致する。

### 手順と結果

| 手順 | 操作主体 | 結果 |
|---|---|---|
| 弱点の抽出と候補の登録 | Claude Code（作業者のセッション） | 候補 `IC-20261124-6e4bf7` |
| 評価計画と課題の固定 | 同上 | 計画 `b66b14bc6714`。開発用 10 件、候補選択用 12 件、封印評価 13 件（うち実物 1 件） |
| 現行方式の基準値 | 同上 | 参照の解決は、どの分割でも 0 件（sandbox-exec での隔離） |
| 候補の生成 | Claude Code（基盤の実行担当、sonnet。基盤の複製の中で実行） | 対象の 1 ファイルだけを変更（+69 行）。外部への呼び出し 1 回、約 32 秒 |
| 評価 | Claude Code（作業者のセッション） | 下の表 |
| 採否 | policy（機械的な判定） | **棄却** |

| 分割 | 参照の解決（現行 → 候補） | 形式・証拠の保全の違反 | 文脈の長さ（現行方式に対する比） |
|---|---|---|---|
| 開発用（実物 4 件を含む） | 0/44 → 43/44 | 0 | 2.41 |
| 候補選択用（合成 12 件） | 0/49 → 47/49 | 0 | **4.21**（上限 4.0 を超えた） |
| 封印評価（実物 1 件＋合成 12 件） | 0/38 → 36/38 | 0 | 4.36 |

- 棄却の理由は「候補選択用の課題で、文脈が長くなりすぎる」。事前に決めた上限（現行方式の平均の 4.0 倍）を超えた。
- 長さの増え方は、主張の本文が極端に長い合成課題（over_budget、各 2 件）に集中している（候補選択用で 28 倍、封印評価で 20 倍）。
  候補は、長い定義を切り詰めずに、予算（24,000 字）いっぱいまで添える。この種類を除くと、1.93 倍と 1.56 倍だった。
- 実物の 5 件では、参照 26 件をすべて解決し、長さは 1.2〜2.2 倍だった（開発用 4 件、封印評価 1 件）。
- 上限の 4.0 倍は、結果を見る前に作業者が決めた値で、根拠は強くない。**結果を見たあとで基準は変えていない。**
- 仮に長さの基準を満たしていても、封印評価の実物が 1 件・1 グループなので、判定は保留になっていた（標本の下限は 3 件・2 グループ）。

### この結果から言えること、言えないこと

- 言える: 仕組みが一巡した。候補の生成、範囲の検査、隔離した評価、機械的な判定、記録が、実物で動いた。主指標が大きく良くなった候補を、
  事前に決めた別の基準で棄却できた。
- 言えない: この候補で修正の質が上がるか（測っていない）。研究能力が上がったか（主張しない）。
  「参照先の定義を添える」という方針が無効だということ（不採用は、この計画の条件でのもの。台帳の `rejected_under` に条件を残した）。
- 棄却は正常な結果として扱う。この候補は基盤に反映していない。

### 評価の独立性について（そのまま書く）

- 作業者（このセッション）は、問題を特定するときに、実物の 5 回すべての集計（参照の件数）を見ている。封印評価に回した実物の 1 件も、
  その集計に入っていた。候補を作った実行担当は別のプロセスで、渡したのは開発用の課題だけだが、評価器と合成課題を設計したのは作業者である。
  したがって、今回の封印評価を「誰も見ていない最終評価」とは呼ばない。
- 候補は 1 件だけ作り、封印評価は 1 回だけ見た。複数の候補から最良を選ぶことはしていない。
- 採点は決定的で、モデルを呼ばない。乱数は、合成課題を作る seed だけで、実行の順序や並列度は結果に影響しない。

### 利用量

- 外部へのモデルの呼び出し: 1 回（候補の生成）。定額契約の中で、費用台帳の換算額は 0.10 ドル（API の定価への換算で、実際の請求額ではない）。
- 評価と判定: モデルの呼び出しなし。1 回の実行は 0.1 秒未満。
- 外部の資料の版の確認: 作業者のセッションから 12 ページを取得した（基盤の費用台帳の外。金額は不明で、無料とは扱わない）。
