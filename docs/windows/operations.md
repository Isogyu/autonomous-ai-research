# Windows と Podman: 日常の起動・停止・復旧

**実機では未確認**（2026-11-25 時点）。`status` は CI の Windows で動かした。`start` と `stop` は、実機で最初に確かめる。
WSL 方式でも、PowerShell からは同じ `scripts\aarctl.ps1` を使う（`AAR_WSL_DISTRO` と `AAR_WSL_REPO` を設定）。
WSL の中からは `.venv/bin/python -m aar.cli ctl …`。

## 起動・停止・状態

| 操作 | コマンド | 内容 |
|---|---|---|
| 起動 | `.\scripts\aarctl.ps1 start` | PostgreSQL（Podman）→ Temporal → 移行 → ワーカー → UI。起動済みのものはそのまま |
| 停止 | `.\scripts\aarctl.ps1 stop` | UI、ワーカー、Temporal を止める。PostgreSQL は動かしたまま |
| 全停止 | `.\scripts\aarctl.ps1 stop --all` | PostgreSQL のコンテナも止める（データは volume に残る） |
| ワーカーの入れ替え | `.\scripts\aarctl.ps1 restart-worker` | コードや設定を変えたあと。実行中の工程は打ち切られ、続きからやり直される |
| 状態 | `.\scripts\aarctl.ps1 status` | サービス、残っている実行用のコンテナ、ポートの応答と待ち受けの範囲 |
| ログ | `.\scripts\aarctl.ps1 logs worker --lines 100` | `var\log\<名前>.log`（追記。自動では消えない） |
| 診断 | `.\scripts\aarctl.ps1 doctor` | 必要なものと、隔離の検証の状態 |

- 止めても、研究の状態は PostgreSQL と Temporal の履歴に残り、`start` で続きから再開される。
- Windows のサービスやタスクとしては登録していない。**PC の再起動やサインアウトのあとは、手で `start` する。**
- スリープの抑止はしていない。電源の設定は変更しない。長い実行の前に、スリープしない時間帯かを確かめる。

## 通知と確認

通知は DB に保存される。Windows の通知やメールは出さない。確認する場所:

- `aar projects list` / `aar projects show <id>`（保留の理由が出る）
- `aar limits`（利用上限の待機。実際の問い合わせと、内部で待機を返した処理は別に記録される）
- Web UI（`http://127.0.0.1:8765`）、Temporal の UI（`http://127.0.0.1:8233`）

## 保留の理由と、すること

| 理由 | 意味 | すること |
|---|---|---|
| `rate_limit` | 利用上限。解除の見込みまで問い合わせない（研究が何件あっても共有） | 待つ。自動で再開する。回避のための再試行はしない |
| `auth` | 認証が切れた | この PC でログインし直してから `aar projects resume <id>` |
| `host_sleep` | 工程の間に、この PC がスリープしていた記録がある | スリープしない状態にしてから `resume` |
| `host_sleep_unknown` | 工程が失敗したが、電源の記録を読めず、スリープの有無を判定できない | `aar doctor` の「ホストの電源の記録」と、失敗の内容を確かめる。原因がコードの失敗なら、直してから `resume`（または `cancel`） |
| `policy_changed` | 方針ファイルが、研究の開始時から変わった | 意図した変更なら、人が `aar projects adopt-policy <id>` で取り込む（前後のハッシュが記録される）。無断では取り込まない |
| `prereg_changed` | 事前登録が変わった | 原因を調べる。再開しない |
| `resource` / `budget` / `setup` | ディスクの空き、費用の上限、設定の不足 | 解消してから `resume` |

隔離が使えない場合（Podman が止まっている、検証していない構成、イメージがない）は、実験の工程が
「隔離の検証をまだ行っていない」などの理由で失敗する。弱い方式には切り替わらない。構成を直して `verify` をやり直す。

## 復旧

| 状況 | 見え方 | すること |
|---|---|---|
| サービスが異常終了した | `status` が「異常終了（記録だけが残っている）」 | `start`（古い記録を片付けて起動し直す）。PID だけでは判断せず、起動時刻も照合している |
| 起動・停止の操作が途中で止まった | 「別の起動・停止の操作が進行中」 | 持ち主のプロセスがいなければ、次の操作が自動でロックを引き取る |
| 実行用のコンテナが残った | `status` が「実行用のコンテナが残っている」 | 実行中の研究がないことを確かめてから `podman rm --force <名前>`。残った実行は成功として記録されていない |
| ワーカーを止めても止まらない | 30 秒待って、子孫ごと強制終了 | 実行中の工程は、次の起動でやり直される。外部への操作（PR の作成など）は冪等キーで重複しない |
| PC が再起動した | すべて停止 | Podman の仮想環境を起動 → `start` |
| Podman の仮想環境だけが止まった | PostgreSQL に接続できない | 仮想環境を起動 → `start`。ホストの電源の記録には現れないので、`host_sleep` にはならない |
| PostgreSQL のコンテナを作り直したい | — | volume（`aar-pgdata`）を消さなければ、データは残る。**volume を消す操作はしない** |

## 多重起動を避ける

- 同じ PC での多重起動は、PID の記録とロックで防ぐ。
- **Mac と Windows の両方でワーカーを動かさない。** 同じ Temporal と DB を共有していなくても、同じ研究を両方で進めたり、
  定期実行（日次の収集、週次の企画）が二重に走ったりする。切り替えの手順は [migration.md](migration.md)。
