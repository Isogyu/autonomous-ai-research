# ADR-0007: 監査の独立性と品質ゲート

- 日付: 2026-11-23
- 状態: 採用

## 決定

**担当の分離** — 研究の実装は Claude Code、監査は Codex。ゲートは「監査担当が実装担当と別の系統であること」を機械的に確かめ、
DB の制約（`auditor <> implementer`）でも同じ担当の記録を拒否する。

**監査担当に渡すもの** — 対象の複製、事前登録、原論文の情報だけ。研究側の結論の文章（批判的検討、報告書）は複製から除く。
主要な数値は生データ（`raw.jsonl`）から別実装で再計算させる。

**結果の受け取り** — 研究独立監査 Skill の台帳（`claims.csv`・`issues.csv`・`recomputed_metrics.csv`）を正とし、構造化して保存する。
決まった値でない判定は「Not Tested」、決まった値でない重大度は「Major」として扱う（軽い方に倒さない）。

**ゲート**（`aar/gates.py`、基準は `config/policy.yaml`）— 監査の構造化結果と機械的な確認だけから合否を決める純粋な関数。

- 研究: 監査が最後まで実行された／Critical・Major が 0 件／主要な主張がすべて Verified か Supported／矛盾する主張がない／
  独立再計算がある／データリークなし／テスト合格／事前登録が未改変／担当が分離／基準が開始時から不変。
- 公開: 点数が基準以上／Critical・Major が 0 件／秘密情報なし／限界・再現手順・ライセンスがある／テスト合格／
  文章の数値が分析結果に由来する。

**ループ** — 不合格なら修正担当が直し、コードやデータに及んだ場合は本実験と分析をやり直してから再監査する。
再監査は毎回すべてを調べ直す。上限回数（研究3回、公開2回）で通らなければ「公開不可」として記録する。
公開向けの修正が研究内容に及んだ場合は、研究監査へ戻す（Git の差分のパスで判定し、修正担当の申告には頼らない）。

**数値の扱い** — 報告書の結果の表とグラフは、分析結果から機械的に作る。文章中の小数は分析結果・事前登録・実行記録と照合する。

**監査の状態** — 「最後まで実行された（completed）」の定義は、利用者の Skill の完了条件に合わせる:
主要な主張に判定が付き、数値と指摘から証拠を辿れ、未実施の範囲が明示され、対象の保全比較が済んでいること。
未実施の範囲があっても、明示されていれば completed。監査担当には、研究が実際に行っている主張だけを台帳に載せるよう指示し、
外部に接続できない監査担当のために、原論文の書誌はオーケストレーターが API から取得した記録を証拠として渡す。
（当初はこの指示が曖昧で、範囲外の事項や書誌の未確認を理由に「部分監査」となり、主要な主張がすべて Verified でも
ゲートを通らなかった。基準は変えず、指示と入力を直した。）

**修正担当に渡すもの** — ゲートを通らなかった回の指摘は重大度にかかわらずすべてと、判定が通らなかった主張の本文。
Critical・Major だけを渡していた当初は、Minor の指摘に対応する副次的な主張が「証拠と矛盾」のまま残り、通らなかった。

**監査担当の環境** — 実験と同じ版の依存関係を入れた Python を監査用に用意する（wheel だけで導入し、導入時にコードを実行させない）。

**再開** — 上限回数で「公開不可」になった研究は、利用者が `aar projects reopen` で、未対応の指摘の修正と監査からやり直せる。
基準は研究の開始時に固定したもののままで、方針ファイルが変わっていれば再開できない。人の介入として記録する。

## 実際の実行で分かったこと（2026-11-23〜24、2 件）

- 2 件とも 1 回目の監査で Major の指摘が出た。独立再計算は 1 回あたり 4,800〜7,700 件、元の値との一致は 99.2%。
- 1 件は公開不可、1 件は再開を経て公開可。止まった原因の多くは基盤側（上の 3 点と、監査用の複製の作り方）だった。
- 公開品質監査は、依存関係の版の不整合、丸めの誤り、探索的分析の表記の誤りなどを指摘した。

## GitHub 公開品質監査 Skill（2026-11-24 に統合）

利用者の Skill「repo-publication-audit」を、公開品質監査の正式な手段にした（`aar/audit/publication.py`）。

- **モードは audit（読み取り専用）。** Skill の improve は使わない。監査担当が自分で直して自分で再監査する形を避け、
  指摘は修正担当に渡し、そのあと最初から監査し直す。
- **テストは監査担当に実行させない**（Skill の audit の決まり）。オーケストレーターが隔離環境で実行した結果を「既存のログ」として渡す。
- **結果の検証。** Skill の決まりに合っているかを機械的に確かめる: 21 内訳がすべてあり範囲内か、合計の検算、
  Critical があれば判定 D・Major があれば C 以下か、公開保留なのに A/B でないか、対象コミットが渡した複製と一致するか、
  報告に決まった節があるか、Skill の4ファイルを読んだ記録が実行ログにあるか。
  合っていなければ正常な監査結果として扱わず、やり直す。3 回試して駄目なら研究は「失敗」で確定する。
- **ゲートの条件を追加。** 正式な Skill による監査で結果が正常であること、公開判定が A か B であること、公開保留でないこと。
  Skill が置かれていなければ保留にする。代用の監査は、点数が良くても通らない。
- **点数の扱い。** Skill は点数による自動の閾値を置かない（判定は証拠・深刻度・公開阻害事項で決める）。
  このシステムの方針にある下限（`min_score`、既定 80）は、Skill の判定に加える追加の条件として残している。
  比べるのは確認済み得点で、保留点は足さない。
- **証跡。** 監査の回ごとに、依頼文、実行ログ（道具の呼び出しの記録）、Skill の報告の全文、構造化した結果、検証の結果を保存する。
  DB には対象コミット、Skill の版（内容のハッシュ）、内訳の点数、保留点、未確認の範囲を残す。正常でなかった試行も消さない。
- **内蔵の検査は補助。** 秘密情報、数値の由来、決まった節、ライセンス、外部データの記録、テストは機械的に検査し、
  Skill に補助の資料として渡す。問題があれば Skill の採点にかかわらず指摘として残る。
- **誰が実行するか。** Skill は Claude Code 用として配布されているが、実装担当（Claude Code）と別系統にするため Codex に
  `SKILL.md` と参照資料を読ませて実行している。スラッシュコマンドとしての呼び出しではない。
  Codex は読み取り専用のサンドボックスで Git の履歴も調べられる。

## 限界

- 監査担当も LLM であり、見落としや誤った指摘があり得る。ゲートは監査の質そのものを保証しない。
- 文章中の数値の照合は小数だけが対象で、整数や言葉による主張は監査担当の確認に頼る。

## 追記（2026-11-24）: 仮説の判定を主張として扱う、意図したリークを区別する

研究3（RP-20261123-2efcc1）は、事前登録の仮説6つのうち2つ（H3・H5）が支持されず、研究自身も「不支持」と報告していた。
それでも研究品質ゲートは「主要な主張が独立に検証されている」「証拠と矛盾する主張がない」で不合格になった。
監査の台帳に仮説の文そのものが主張として載り、支持されなかった仮説が Contradicted と記録されたためである。
この扱いでは、否定的な結果を正しく報告した研究が1件も通らない。要件（支持されなかった仮説を省かない、結論ありきにしない）と逆の圧力になる。

また、同じ研究は「リークを意図的に入れると精度がどう変わるか」を調べるもので、監査は「リークを確認した（意図した条件）」と報告し、
ゲートの「データリークが確認されていない」も不合格になった。

対応として、監査への指示（`aar/audit/research.py`）を次のように直した。ゲートの条件と数値は変えていない。
- 台帳に載せるのは、仮説の文ではなく、**仮説についての研究の判定**（支持・不支持・判定保留）。再計算が研究の判定と一致すれば Verified、
  食い違えば Contradicted。研究が「支持」と言っているのに証拠が支えない場合は、これまでどおり通らない。
- 「データリークあり」とするのは、研究自身の評価を無効にする意図しない混入だけ。実験の条件として明記されたリークは該当しない。

研究1・2では仮説がすべて支持されていたため、この問題は表に出ていなかった。
