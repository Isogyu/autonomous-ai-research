# ADR-0013: 社内向けの発信（Teams）— 投稿候補を構造化データで持ち、人が確かめてから出す

- 日付: 2026-11-25
- 状態: 提案（初期実装。**送信は実装していない**。Teams での表示、社内の環境、読者のニーズは未確認）
- 番号について: 0011 と 0012 は、未マージの PR #11・#12 が使っている。

## 背景

収集・研究した情報を、社員の理解、技術の選定、業務での試行に役立てたい。これまでの発信先は GitHub の PR だけで、
対象は研究の成果物に限られていた。社内向けでは、実験済みの成果だけでなく、一次情報に基づく情報の紹介も扱う。
投稿の数や見栄えは成果にしない。読者のニーズと、実際に役立ったかを確かめながら、段階的に作る。

## 決定

1. **投稿候補 1 件を、構造化データ 1 つで持つ**（`briefs/<id>/brief.yaml`、`aar.brief.model`）。対象の読者、目的、検証の状況、
   出典と確認日と対象の版、制約、確かめていない点、既存の情報からの変化、今知らせる理由、似た投稿の有無を必須にする。
2. **目的と検証の状況を、別の項目にする。** 目的は「知る・判断する・試す」。検証の状況は「情報紹介・未再現」「第三者の検証を紹介」
   「自環境で検証済み」「表示確認用の架空データ」。自分たちの実測（`evidence`）がなければ「検証済み」にできず、実測があるのに
   紹介として出すこともできない（他者の結果と自分たちの実測を混ぜない）。確かめていない内容を確かめたように読める表現は、入力の検証で拒否する。
3. **カード・本文・詳細ページは、データを決まった手順で並べるだけで作る**（`aar.brief.render`）。モデルに文章を書き直させず、
   画像生成も使わない。だから、カードと詳細ページは食い違わず、データにない数値や URL は出力に現れない。
4. **図解カードは SVG のテンプレート。** 幅 1024、高さは内容で決まり、1024 を超える内容は拒否する（文字を小さくしない）。
   文字の大きさに下限を置き、条件・制約はカードの本体に、ほかの文字と同じ大きさで入れる。検証の状況は、色だけでなく文字と枠の形で示す。
   画像だけに情報を閉じ込めない: 投稿の本文に、図の内容・要点・検証の状況・制約・出典を文章で入れる。
5. **状態は、追記だけの記録で持つ**（`briefs/ledger.jsonl`。前の行のハッシュを持つ）。下書き → レビュー待ち → 承認済み。ほかに保留、棄却、
   検索用の保存。承認は内容のハッシュに結び付き、承認のあとで内容が変わると効かなくなる。**承認できるのは人だけ。**
   操作した主体（human / claude_code など）は省略できない。
6. **新しいサービスも、DB の表も、管理画面も足さない。** 置き場所はリポジトリの中のファイルで、差分は Git で見る。
   レビューは、ふつうの PR のレビューと同じ形でできる。
7. **既存の検査を通す。** 秘密情報と作業用のパス（`workspace.SECRET_PATTERNS`）、メールアドレスと第三者の文章の転載
   （`publish.required` の照合。基準は公開前の検査と同じ）を、レビューに出す前と承認の前に確かめる。照合元の文章が手元になければ、
   承認する人の申告が要る。検出した一致は、申告では通らない。社内の機密にあたるかどうかは機械では分からないので、承認する人が確かめて申告する。
8. **送信しない。** Teams への投稿は人が行い、その事実を記録する（`aar brief record-post`）。無人の定期配信は作っていない。
   方針ファイル（`config/policy.yaml`）は変更していない。
9. **訂正は、元を書き換えずに、訂正版を別の候補として作る。** 訂正版は元の id を持ち、承認をやり直す。詳細ページに訂正の履歴が出る。
10. **感想は、少数を手で記録する**（`briefs/feedback.jsonl`）。個人を特定する書き方は受け付けず、答えは任意。点数にはまとめない。

## 理由

- 確かめていない情報が、変換の途中で確かめたように見えるのが、いちばん避けたい失敗。文章を作り直す工程を置かなければ、起きない。
- 承認を内容に結び付けないと、承認のあとの書き換えが、そのまま出てしまう（研究の監査で、対象のコミットを固定しているのと同じ考え方）。
- 読者のニーズを確かめる前に、配信の仕組みを大きく作らない。まず、少数の読者に見せられるプレビューがあればよい。

## 影響と限界

- **読者の役に立つかどうかは、何も確かめていない。** 対象の読者も、ニーズも、いまは仮定（サンプルの 3 件はすべて `evidence: assumed`）。
- Teams での表示（デスクトップ、モバイル）、画像の取得、Adaptive Card の表示、社内での Workflows の利用の可否は未確認。
  Teams のカードの画像は SVG に対応しない（公式の文書）。PNG への変換は実装していない（フォントと変換の道具が環境に依る）。
- 詳細ページの保存先は未定。Markdown をローカルに出すだけで、URL は作らない。
- 入力の検証は、形と、決まった表現を見るだけ。内容が正しいか、読者に関係するかは、人が判断する。
- YAML では、空白のあとの `#` から後ろがコメントになる。値を引用符で囲まないと文が欠ける（読み込みで検出して止める）。
- 文字の大きさの下限（32）、カードの大きさ（1024）、項目の数の上限は、設計上の提案。実機と読者で確かめて直す。
