# ADR-0011: 基盤の改善候補を、台帳と保護された評価で扱う

日付 2026-11-25。状態: 提案（初期実装。稼働中の基盤には自動で反映しない）。

## 背景

基盤側の問題（修正担当への文脈の取り落とし、監査の指示の不備、利用上限の時刻の読み違いなど）は、これまで実行の記録を人や作業者が読んで見つけ、
その場で直してきた。直した効果は、次の実行の印象でしか確かめていない。
外部の研究（自己改善型のハーネスなど）を取り込むにも、この基盤で効くかどうかを比べる場所がなかった。

## 決定

1. **台帳を PostgreSQL に置く**（`improvement_*` の表）。候補、発見元、評価計画、実行、判定、操作の記録を持つ。
   評価計画・実行・判定・操作の記録は追記だけにし、DB のトリガーで UPDATE と DELETE を拒否する。
2. **操作主体の種類を必須にする**（human / claude_code / codex / scheduler / policy）。省略はできない。AI の操作を人の操作として記録しない。
3. **候補が変更できるのは、対象ごとの許可リストのファイルだけ**（`aar.improve.targets`）。保護領域（品質ゲート、公開の判定、事前登録の検証、
   評価器と採否の基準、権限・隔離・送信先、利用上限・予算、移行、テスト、CI）は、許可リストより優先して拒否する。差分は Git で確かめる。
4. **評価する側は、候補のコードを自分のプロセスに読み込まない**。候補のファイルを Git から取り出し、隔離した別プロセス
   （`python -I -S`。macOS では sandbox-exec でネットワーク・書き込み・研究の記録の読み取りを禁じる）で動かして、出力の文字列だけを受け取る。
   別プロセスに渡すのは課題の入力だけで、正解と採否の基準は渡さない。
5. **採点は決定的で、モデルを呼ばない**。採否は、候補を作る前に固定した計画の基準を機械的に当てはめる。
   結果は「採用候補」「棄却」「保留」。採用候補になっても、基盤への反映には人の承認とレビューが別に要る。
6. **評価計画は、内容・課題・評価器のハッシュで固定する**。課題か評価器が変わったら、その計画での実行は失敗として記録し、比較しない。
   評価器の変更は、候補とは別の変更として扱う。
7. **課題は、開発用・候補選択用・封印評価に分ける**。同じ研究の複製は、事前登録の内容で同じグループにまとめ、別の分割に分けない。
   封印評価の合成課題は、リポジトリの外に置いた seed から作る。封印評価を見た回数は、候補の系統ごとに数える。
8. **Temporal のワークフローは変えない**。改善の一巡は CLI から同期的に進め、冪等キー（実行の `run_key`）と候補の状態で再開する。
   ワークフローを変えないので、既存の履歴との互換性の問題は起きない。
9. **新しい基盤は入れない**。グラフ DB、分散基盤、エージェントのフレームワークは使わない。既存の GuardedRunner と費用台帳を使う。

## 理由

- 改善の主張を、変更の前に決めた基準で判定できるようにするため。監査の点数やテストの合格数を、研究能力の向上の証拠にしない。
- 自分を採点する処理を、採点される側が変えられると、評価の意味がなくなる。プロンプトでの禁止ではなく、差分の検査とプロセスの分離で止める。
- 最初の対象を、モデルを呼ばずに採点できるもの（渡す文脈の完全さ）にしたのは、利用枠を使わず、結果が再現できるため。

## 影響と限界

- 測っているのは「修正担当に渡す文脈の完全さ」で、修正の質、研究の質、科学的な成果ではない。
- 候補を**作る**側（実行担当の CLI）は、基盤の複製を作業ディレクトリにして動かすだけで、OS による読み取りの制限はかけていない。
  同じ利用者の権限で動くので、封印評価の課題の場所を探して読むことを、仕組みとしては防げていない。評価する側の隔離とは強さが違う。
- Linux では sandbox-exec がなく、隔離は「別プロセスにするだけ」になる。その実行は、計画が求める隔離を満たさないので、採否は保留になる。
- 実行担当の CLI は外部と通信する。複製と作業の説明の内容は、モデルの提供元に送られる。
- 移行 0006 は表を足すだけで、既存の表は変えない。稼働中の DB への適用は、マージ後に人が行う。
