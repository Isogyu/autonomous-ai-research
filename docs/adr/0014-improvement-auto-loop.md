# ADR-0014: 改善の自動ループ — 1 巡の自動実行、論文からの仮説、対象ごとの評価器

- 日付: 2026-11-26
- 状態: 提案（実装済み。**実物の 1 巡は、まだ一度も動かしていない**。台本の実行担当でのテストだけ）

## 背景

当初の目的は、基盤（ハーネス）の自己改善と、論文の内容を取り入れた改善を、自動で繰り返すことだった。ADR-0011 の時点では、
人がコマンドを 1 つずつ実行する形で、論文は領域と資料を登録しただけだった。足りなかったのは次の 3 つ。

1. 論文の手法を「この基盤のどの問題に効くか」という仮説に直す工程。
2. 改善の対象ごとの評価器（対象が 1 つしかなかった）。
3. この基盤での比較を、人の操作なしで最後まで進めること。

## 決定

### 1. 1 巡を 1 つの処理にする（`aar improve cycle`、`aar.improve.auto.run_cycle`）

論文から仮説を拾う → 記録から弱点を拾う → 候補を登録 → 対象ごとに評価計画を固定して基準値を測る → 候補を生成 →
候補選択用の課題で評価 →（通ったものだけ）封印評価 → 採否 → 採用候補は、差分を書き出して通知。

- **自動にするのは、採用候補を出すところまで。** 基盤への反映（マージ、配備）は、人がレビューして行う。
- 済んだ工程は繰り返さない（候補の状態、実行の `run_key`、計画ごとの判定の有無で判断する）。途中で止まっても、次の巡が続きから進める。
- 止まる条件（その巡は、理由を記録して終わる。弱い方式には切り替えない）:
  隔離が使えず現行方式の基準値を測れない／利用上限に達した／候補を作る側の隔離を人が認めていない。
- 上限: 1 巡で作らせる候補は 1 件、読む論文は 3 件（設定で変えられる）。同じ発見元からの候補の上限は、従来どおり。

### 2. 候補選択用で外れた候補は、封印評価を見ずに棄却する

これまでは、4 つの実行（現行・候補 × 候補選択用・封印評価）がそろうまで「保留」だった。自動で回すと、通る見込みのない候補にも
封印評価を見せることになる。候補選択用の課題だけで分かる違反（動かない、形式や証拠の保全、課題ごとの後退、長さ）は、その時点で棄却する。
4 つがそろったときの結論は、これまでと同じ。

### 3. 論文は「仮説」として取り込む。証拠にはしない（`aar improve papers`、`ideas_from_papers`）

- 収集済みの論文から、対象か領域に関係しそうなものを語で粗く選び、実行担当に要旨を読ませて、決まった形で答えさせる:
  試せる対象（なければ none）、関係する領域、使う考え方、仮説、副作用、著者が実測で示しているか、（対象が無いとき）要る評価器。
- 道具は渡さない。作業ディレクトリは空。要旨は資料として囲み、そこに書かれた命令に従わないよう指示する。
- **論文の結果は、著者の環境での主張。** この基盤で効くかは、ほかの候補と同じ評価で決める。候補には「効果は確かめていない」と書く。
- 台帳に残すのは、こちらで書いた短い要約と、論文の識別・版・読んだ範囲（要旨だけ）。**要旨の文章と数値は写さない**（テストで確かめている）。
- 読んだ論文は、資料の表に結果つきで残し、読み直さない。
- 試せる対象が無い仮説は、捨てずに、「評価器があれば試せた仮説」として領域ごとに数える（`aar improve backlog`）。
  どの評価器を作れば、試せる仮説が増えるかの手がかりにする。

### 4. 評価器を、対象ごとに足せる形にする（`evalkit.Spec`）

- 対象 1 つにつき、課題の作り方（実物・合成）、採点、評価計画の値、候補を作る側に見せる説明を持つ `Spec` を 1 つ用意する。
- 採点の結果の項目の名前は対象に依らず共通にし、採否の判定（`decide`）は対象を知らずに済むようにした。
- **評価器は、人が書いてレビューする。** 自動では作らない。採点される側（候補を作る実行担当）が、採点の方法を作れるようにはしない。
  評価器のファイルは保護領域で、内容のハッシュを評価計画に固定する。
- 2 つ目の対象として「失敗したときのログの抜粋」（`log_excerpt`）を足した。現行の動作（各流れの末尾を渡す）を 1 つの関数に出しただけで、
  動作は変えていない。測るのは、原因を示す行が抜粋に入っている割合。ログにない内容を作らないこと、終わりの行を落とさないこと、
  長くしないことが条件。**実物の課題をまだ作れない**（保存している実行ログは末尾だけで、正解を決められない）ので、
  この対象の候補は、指標が良くても「保留」までにしかならない。

### 5. 定期の実行は、既定で無効（`AAR_IMPROVE_AUTO`）

Temporal に `ImprovementWorkflow`（1 巡を実行するだけ）を足し、設定を有効にしたときだけ、週 1 回の定期実行を登録する。
既存のワークフローは変えていないので、既存の履歴の再生には影響しない。

## 変えていないもの

- 採否の基準（改善幅、水準、長さの上限 4.0 倍、標本の下限 3 件・2 グループ、封印評価を見てよい回数）。
- 保護領域と、候補が変更できる範囲。評価計画を、候補を作る前に固定すること。
- 隔離: 計画が求める隔離（検証済みの Podman）が使えなければ、評価しない。
- 候補を作る側の隔離は未完成のままで、**生成は既定で拒否する**（`AAR_IMPROVE_ALLOW_UNISOLATED_GENERATOR`）。
- 最初の候補（`IC-20261124-6e4bf7`）の棄却。

## 限界（そのまま読んでほしい）

- **既定の設定では、このループは最後まで回らない。** 生成が拒否され、Podman の隔離の検証が済んでいない環境では基準値も測れない。
  回すには、人が、隔離の検証（`aar podman verify`）を通し、候補を作る側の隔離なしでの生成を認める設定をする必要がある。
- 2 つの対象とも、いまは採用候補に届かない: `fix_context` は実物の標本が 1 件、`log_excerpt` は 0 件。
  つまり、**いま自動で回して得られるのは、棄却と保留の記録まで。** 標本が増えるか、実物の課題を作れるようになるまで、採用候補は出ない。
- 評価器は 2 つだけ。どちらも「渡す情報の完全さ」を測るもので、修正の質、研究の質、科学的な成果は測らない。
  論文の考え方の多くは、いまの対象には当てはまらない見込み（当てはまらないものは、要る評価器とともに数える）。
- 論文は要旨しか読んでいない。当てはめの判断はモデルが行うので、誤ることがある。誤った仮説は、評価で棄却されるだけで、基盤には入らない。
- 評価器が変わったので、評価器のハッシュが変わる。固定済みの評価計画での新しい実行は、比較されない（決まりどおり）。
- 実物の実行担当での 1 巡、実物の Podman での評価、定期の実行は、どれも動かしていない。
