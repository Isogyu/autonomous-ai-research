# ADR-0009: 公開前の必須項目は、決定的な検査と監査担当の申告の両方で確かめる

- 日付: 2026-11-24
- 状態: 採用

## 状況

同じ公開候補に、公開品質監査 Skill を2回実行したところ、Major の指摘の有無が分かれた（研究2）。
片方は「監査記録に原論文の要旨が全文で入っており、再配布の根拠が未確認」を Major として公開保留にし、
もう片方は Critical・Major なしの判定 B とした。原因を調べた結果は次のとおり。

| 比べたもの | 単独の実行 | パイプライン内の実行 | 差 |
|---|---|---|---|
| Skill の内容 | `repo-publication-audit@9f68540f8367` | 同じ | なし |
| 依頼文 | 7,560 字 | 対象のパスと「補助の資料」以外は同じ | 下の2点だけ |
| 補助の資料: 数値の由来 | 由来不明 7 件 | 0 件 | 単独実行では原論文の数値を渡さなかったための誤検知 |
| 補助の資料: テスト | 「実行していない」 | 14 件合格（隔離環境） | 単独実行ではテストを実行しなかった |
| 対象のコミット | `a0538c4` | `0d7bf23`（監査報告を足した次のコミット） | 要旨の入ったファイルはどちらにもある |
| 実行条件 | Codex、read-only、既定のモデル | 同じ | なし |
| 要旨のファイルを読んだか | 読んだ（`cat` で全文を表示） | 読んだ（同じく全文を表示） | **なし** |
| 判断 | 再配布の根拠が未確認 → Major、公開保留 | 権利の問題として扱わなかった | **ここだけが違う** |

つまり、**入力の差では説明できない。同じ文章を読んだうえで、それを権利の問題とみなすかどうかの判断が実行ごとに揺れた。**
Skill は「権利・公開許諾の根拠」を採点項目にしているが、項目ごとに確認結果を答えさせる形にはなっておらず、
見て問題にしなかった場合と、見ていない場合が、結果の上で区別できなかった。

## 決定

見逃すと取り返しがつかない項目を「公開前の必須項目」と定め、2通りで確かめる。どちらも方針ファイルでは無効にできない。

### 1. 決定的な検査（`aar/publish/required.py`）

言語モデルを使わず、毎回同じ手順で調べる。同じコミットなら結果は必ず同じになる。

| 項目 | 調べること |
|---|---|
| 秘密情報 | 既知の形式のキー・トークン・秘密鍵、秘密情報を入れる名前のファイル。追跡ファイルと全履歴の差分 |
| 個人情報 | 作業用パス、ファイル中のメールアドレス、全コミットの作成者・コミッターのメールアドレス |
| 第三者の文章 | 原論文の要旨・取得済みの本文と、追跡ファイル・全履歴のテキストを照合。空白を除いて連続 300 文字以上の一致を収録とみなす |
| ライセンス | LICENSE の有無と既知のライセンス文との一致、README の記載、外部データの取得記録のライセンス欄 |
| 第三者のデータ | `data/external/` が Git に入っていないこと（現在と全履歴）、取得記録とハッシュの一致、取得し直すスクリプト |

結果は項目ごとに ok / violation / unverified。照合する文章が手元にない、ライセンスの種別を確かめられない、といった場合は
ok にせず unverified にする。

### 2. 監査担当の申告（`aar/audit/publication.py`）

Skill の結果に、必須項目ごとの確認結果（問題なし / 問題あり / 未確認）と根拠を必ず書かせる。
- 5項目のどれかが欠けている、「問題なし」なのに調べた方法が書かれていない、「問題あり」なのに対応する指摘がない、
  という結果は「正常な監査結果ではない」として扱い、やり直す（既存の仕組み）。
- 「未確認」は正直な申告なので結果としては正常だが、**未確認が1つでも残れば公開品質ゲートを通さない**。
- 決定的な検査の結果は監査担当にも渡す。決定的な検査が違反とした項目を監査担当が「問題なし」とした場合は、
  食い違いとして記録に残す（監査の見逃しの実測になる）。

### 3. ゲート

公開品質ゲートに2つの確認を足した。「公開前の必須項目の決定的な検査に違反がない」「公開前の必須項目に未確認が残っていない」。
違反と未確認は Major の指摘（秘密情報は Critical）として修正担当に渡り、修正のあと最初から監査し直す。
既存の基準は1つも外していない。

## 分かっている限界

- 決定的な検査は、機械的に確かめられる範囲しか見ない。言い換えた転載、図表の転載、コードの転載、既知でない形式の秘密情報は検出できない。
  それらは引き続き Skill の監査の役割で、実行ごとに揺れ得る。
- 第三者の文章の照合元は、原論文の要旨と取得済みの本文だけ。ほかの文献からの転載は照合しない。
- 履歴にだけ残っている違反は、ファイルの編集では直せない。修正担当には直せないと伝え、ゲートは通さない。
  履歴の書き換えは事前登録のコミットの記録と衝突するので自動では行わず、人が判断する。
- 監査担当の「問題なし」の申告が本当に調べた結果かどうかは、根拠の記述と実行ログでしか確かめられない。

## 追記（2026-11-24）: ライセンスの一次資料

公開データを使う最初の研究（RP-20261123-775b36）で、決定的な検査は「取得記録にライセンス欄がある」だけで通し、
監査担当は「申告であって提供元の表示ではない」として未確認にした。監査担当の判断が正しい。

- 成果物を作る工程と、公開向けの修正の前に、基盤が提供元のページ（カタログの `license_url`）からライセンスの文言を、
  PyPI から版を固定した依存パッケージのライセンスを取得し、`docs/third_party_licenses.md` と `docs/license_evidence.json` に残す
  （取得元・日時・ページのハッシュ・文言の抜粋）。修正担当は外へ取りに行けないので、基盤が行う。
- 決定的な検査は、この記録で裏づけられない外部データのライセンスを「未確認」にする。
- 記録はリポジトリの中にあり、修正担当が書き換えられる。ハッシュの控えをリポジトリの外（`audits/`）に持ち、
  一致しない記録は裏づけに使わない。
- カタログにない外部データ（`license_url` がない）は、未確認のままになる。合格させるには、提供元のページをカタログに登録する。
