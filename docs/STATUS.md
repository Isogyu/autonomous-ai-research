## 品質の強化と実地検証（2026-11-24、ブランチ feat/reliability）

### 1. 公開品質監査の揺れの原因と対策

原因の調査は [ADR-0009](adr/0009-required-checks-and-audit-variance.md) にまとめた。要点は、Skill・依頼文・実行条件は同じで、
どちらの実行も要旨の入ったファイルを全文表示していたのに、権利の問題とみなすかどうかの判断だけが違ったこと。入力の差では説明できない。

対策は2つ。どちらも方針ファイルでは無効にできない。
- **決定的な必須検査**（秘密情報・個人情報・第三者の文章・ライセンス・第三者のデータ）。同じコミットなら結果は必ず同じ。
- **監査担当の申告**。必須項目ごとに「問題なし／問題あり／未確認」と根拠を書かせ、未確認が残ればゲートを通さない。

既存の研究への適用結果（`aar projects required-check`、読み取りだけ）:

| 対象 | 秘密情報 | 個人情報 | 第三者の文章 | ライセンス | 第三者のデータ |
|---|---|---|---|---|---|
| 研究1（公開可と判定済み） | ok | ok | **違反**（履歴に要旨 1,615 字、本文 1,534 字） | ok | ok |
| 研究2（公開可と判定済み） | ok | ok | **違反**（履歴に要旨 1,566 字） | ok | ok |
| 検証用の複製（履歴から除去済み） | ok | ok | ok | ok | ok |

研究1・2は、現在のファイルからは要旨を除いてあるが、Git の履歴に残っている。ブランチを push すれば履歴ごと公開されるので、
いまの基準では公開前に履歴の対処が要る。履歴の書き換えは事前登録のコミットの記録と衝突するため自動では行っていない。

実物の監査3回（検証用の複製）では、監査担当は5項目すべてを根拠つきで「問題なし」と申告し、決定的な検査とも一致した。
決定的な検査と監査担当が食い違う例、監査担当が「未確認」と申告する例は、実物では出ていない（自動テストで確認）。

- **両方とも、いまの必須検査では違反**（上の表）。判定のあとに検査を足したため、ゲートには反映されていない。
- 研究1: 最後の独立監査が「反映が必須」とした原論文の情報（本文から分かった対応比較の数値）が、報告書に反映されないまま通っている（重大度 Minor のため）。
- 研究2: `docs/limitations.md` が、修正の途中で内容を失って書き直された状態のまま公開候補に入っている。「監査の詳細は本リポジトリにない」など実態と合わない記述が残る。

いまの基準では両方とも公開前に対処が要る。

### 4. 研究3（本文を使った初の研究）で見つかった基盤側の問題

研究3（2efcc1）は独立監査 3 回で「公開不可」になった。再計算は 6,761 行で一致していたが、次の理由で通らなかった。
- 仮説 6 つのうち 2 つが支持されず、研究も「不支持」と報告していたのに、台帳では「証拠と矛盾する主張」と数えられた。
- リークの影響を調べる研究なので意図的にリークを入れているが、「データリークあり」と数えられた。
- 3回目の監査で Major 2 件（置換重要度の中間結果が保存されていない、生成設定の事前固定を確認できない）。こちらは研究側の問題で、

## 安全上の制限

- エージェント CLI は外部と通信する。読ませたファイルの内容はモデルの提供元に送られる。
- プロンプトインジェクションへの備えは、道具と権限を絞ることが主で、文章による指示は補助。
- 実験用イメージの構築時は、エージェントが書いた `requirements.txt` に従ってパッケージを導入する（コンテナ内、ネットワークあり）。
- 秘密情報の検査はパターン照合。未知の形式の鍵は見つけられない。
- 監査担当も LLM であり、見落としや誤った指摘があり得る。品質ゲートは監査の質そのものを保証しない。
- 詳細は [ADR-0006](adr/0006-security.md)。
